## 二、关键发现

### 2.1 🔴 INT8 在 CPU 上不加速，反而略慢（已 3 轮验证）

**验证实验**（2026-07-01）：YOLOv5s FP32 vs INT8 各跑 3 轮推理，snpe-diagview 取 Total Inference Time。

| 轮次 | FP32 | INT8 | INT8/FP32 |
|------|------|------|-----------|
| Round 1 | 6,959 ms | 9,849 ms | **+41.5%** ⚠️ 冷启动 |
| Round 2 | 7,047 ms | 7,233 ms | **+2.6%** |
| Round 3 | 7,132 ms | 7,323 ms | **+2.7%** |
| **Avg (R2-R3)** | **7,090 ms** | **7,278 ms** | **+2.7%** |

> Round 1 INT8 异常慢是冷启动效应（反量化 kernel 首次加载无缓存），排除后两轮，INT8 稳定慢 **2.6-2.7%**，3 轮无一例外。

**原因**：x86 CPU 没有 INT8 向量化指令（如 ARM NEON dot-product 或 Hexagon HVX）。SNPE 在 CPU 上做 INT8 推理需要**运行时反量化**（INT8→FP32→计算→FP32→量化回 INT8），这个额外开销导致比纯 FP32 推理还慢。

```
x86 CPU 上的 INT8 "伪加速"：
  权重 INT8 → 反量化为 FP32 → FP32 矩阵乘法 → 结果量化回 INT8
                 ↑ 多这一步 ↑

真正的加速路径（需 DSP/HTP 硬件）：
  权重 INT8 → INT8 矩阵乘法(硬件指令) → 结果 INT8
               ↑ 一步到位，2-4x ↑
```

**结论**：INT8 加速必须依赖 **DSP/HTP 硬件**（Hexagon HVX / ARM NEON dot-product）。在 VM x86 上 INT8 的意义仅在于**模型体积压缩**（-75%，29MB→7.2MB），不带来推理加速。**端侧 AI 芯片的硬件 accelerators 才是 INT8 的核心价值。**

### 2.2 🔴 当前 VM 离实时推理差 100-200 倍

| 场景 | 所需延迟 | 当前延迟 | 差距 |

**在 VM 上，实时视频推理完全不可能。每处理一帧视频需要约 10 秒（YOLO 7s + Inception 3.3s）。**

## 四、对障碍规避管线的可行性评估

### 4.1 管线耗时分析（VM x86 CPU）

```
视频帧 → YOLOv5(7.0s) → 检测到障碍? → InceptionV3(3.3s) → LLM(?) → 决策
                    ↓
              无障碍 → 跳过分类 → 下一帧
```

| 场景 | 耗时 | 帧率 |
|------|------|------|
| 无障碍物（仅 YOLO） | 7.0s | 0.14 fps |
| 有障碍物（YOLO+分类） | 10.3s | 0.10 fps |
| 有障碍物（YOLO+分类+LLM） | 10.3s + LLM | <0.1 fps |

### 4.2 真机（QCS8550）可行性预估

```
QCS8550 HTP 预估:
视频帧 → YOLOv5-INT8(5-25ms) → InceptionV3-INT8(5-20ms) → LLM-INT4(0.5-3s)
                                                    ↓
                                              管线总延迟: 0.5-3s
```

| 因素 | 评估 |
|------|------|
| 障碍检测延迟 | 🟢 YOLO 5-25ms，接近实时 |
| 障碍分类延迟 | 🟢 InceptionV3 5-20ms，可接受 |
| LLM 决策延迟 | 🟡 1B 模型 0.5-3s，需要优化（流式/缓存） |
| 管线总延迟 | 🟡 1-3 秒，适合辅助导航，不适合高速自动驾驶 |

### 4.3 LLM 端侧部署关键约束

| 约束 | 数值 | 影响 |
|------|------|------|
| QCS8550 RAM | 通常 8-16GB | INT4 1B 模型可跑，7B 不可 |
| HTP 推理速度 | 10-50 ms/token | 50 tokens 决策需 0.5-2.5s |
| INT4 精度损失 | 通常 <5% | 结构化决策场景可接受 |
| LPAI Backend | 需要 QNN ≥ 2.20 | SDK v2.22.6 支持 |

## 七、下一步：Phase 3 — LLM 端侧部署

基于 Day 5 数据，Phase 3 路线：

1. **选模型**：TinyLlama-1.1B（最小可用）或 Qwen2-1.5B（中文好）
2. **导出 ONNX**：PyTorch → ONNX（需适配 QNN LPAI）

> ⚠️ 关键风险：QNN LPAI backend 对 LLM 的支持度未知，可能需要在 Day 6 探索替代方案（如直接用 llama.cpp 在 VM 上跑 CPU 推理做功能验证）。
