# 端侧障碍规避系统 — 完整项目计划

> 课题：基于端侧 AI，输入视频流，识别路障 → 自主路线规划 → 规避障碍
> 底层硬件目标：高通 QCS8550（美格 SNM970）手机端芯片
> 当前开发环境：Mac M5 Pro (24GB) + UTM Ubuntu 22.04 x86_64 (8GB)
> 创建日期：2026-07-01
> 最后更新：2026-07-03（整合 LLM 产品化替代路线）

---

## 一、项目架构

### 1.1 原架构（已废弃）

```
┌─────────────────────────────────────────────────────────────┐
│                      视频输入 (30fps)                        │
│                          │                                   │
│                    逐帧提取 + 前处理                          │
│                          │                                   │
│          ┌───────────────┼───────────────┐                   │
│          ▼               ▼               ▼                   │
│   ┌──────────┐   ┌──────────────┐   ┌──────────┐            │
│   │ YOLOv5s  │   │ InceptionV3  │   │   LLM    │            │
│   │ 障碍检测 │   │  障碍分类    │   │ 路线决策 │            │
│   │ (检测框) │   │  (细分类别)  │   │ (规划)   │            │
│   └────┬─────┘   └──────┬───────┘   └────┬─────┘            │
│        │                │                │                   │
│        └────────────────┼────────────────┘                   │
│                         ▼                                    │
│                   决策融合 → 规避动作                         │
│               (减速/绕行/停车/变道)                           │
└─────────────────────────────────────────────────────────────┘
```

> ⚠️ 问题：LLM 直接位于实时决策闭环中，推理时延抖动大、输出自由度高、HTP 工具链当前不可用，单点阻塞整个系统。

### 1.2 新架构：双层决策（推荐）

```
                        视频流 (30fps)
                              │
                        逐帧提取 + 前处理
                              │
                ┌─────────────┼─────────────┐
                ▼             ▼             ▼
          ┌──────────┐ ┌──────────────┐
          │ YOLOv5s  │ │ InceptionV3  │
          │ 障碍检测 │ │  障碍分类    │
          └────┬─────┘ └──────┬───────┘
               │              │
               └──────┬───────┘
                      ▼
              结构化场景描述 (JSON)
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
   ┌──────────────┐       ┌──────────────┐
   │  实时决策层   │  ◄──  │ LLM 高层策略层│
   │  规则引擎/    │       │  结构化小脑   │
   │  状态机/      │       │  非实时顾问   │
   │  轻量策略     │       │  复杂场景推理 │
   └──────┬───────┘       └──────┬───────┘
          │                      │
          │       融合规则        │
          └──────────┬───────────┘
                     ▼
              最终规避动作
       (STOP / SLOW / BYPASS / WAIT …)
```

**关键设计原则：**
- 实时层 **不需要 LLM 也能独立工作**
- LLM 层作为非实时顾问，提供策略建议
- LLM 缺失/超时时，自动回退到规则动作
- 输出空间固定为 8 个动作（见下文），可控可评测

## 二、技术栈

| 层 | 工具/模型 | 作用 |
|----|-----------|------|
| 推理引擎 | 高通 SNPE/QNN SDK v2.22.6（开发机）/ 待匹配板端 v2.0.1 | 模型转换、量化、推理 |
| 目标检测 | YOLOv5s | 检测障碍物在画面中的位置 |
| 图像分类 | InceptionV3 | 对检测到的障碍物做细粒度分类 |
| 实时决策 | 规则引擎 / 状态机 / 代价函数 | 毫秒级避障动作决策 |
| 高层策略 | TinyLlama-1.1B（结构化小脑）| 复杂场景策略建议、可解释推理 |
| 部署格式 | DLC (Deep Learning Container) | 高通芯片原生格式 |
| 量化 | INT8 (视觉) / INT4 (LLM) | 压缩模型适配端侧资源 |

### LLM 输入输出协议

**输入（结构化场景描述）：**
```json
{
  "obstacles": [
    {"type": "cone", "x": 0.42, "y": 0.63, "w": 0.12, "h": 0.20, "distance_est": 2.3},
    {"type": "trash_bin", "x": 0.71, "y": 0.58, "w": 0.10, "h": 0.18, "distance_est": 1.4}
  ],
  "free_space": {
    "left": 0.68,
    "center": 0.12,
    "right": 0.55
  },
  "ego_state": {
    "speed_level": "slow",
    "heading": "forward"
  }
}
```

**输出（固定动作集合）：**
```json
{
  "action": "BYPASS_LEFT",
  "confidence": 0.84,
  "reason": "center blocked, left corridor wider than right"
}
```

**动作集合（共 8 个）：**
```
STOP        — 紧急停车
WAIT        — 等待观察
SLOW_DOWN   — 减速慢行
KEEP_CENTER — 保持居中
TURN_LEFT   — 左转
TURN_RIGHT  — 右转
BYPASS_LEFT — 从左侧绕行
BYPASS_RIGHT— 从右侧绕行
```

### 融合层规则

```
如果实时层判定危险阈值超限：
  直接 STOP / SLOW_DOWN（忽略 LLM）

如果实时层无硬冲突，且 LLM 给出高置信建议（confidence > 0.7）：
  采纳 LLM 建议

如果 LLM 缺失 / 超时 / 低置信度：
  回退到规则引擎动作
```

## 四、HTP 现状与应对策略

### 核心矛盾

```
板端 /vendor:  QNN HTP runtime  v2.0.1.220706112757_38277
手头 SDK:      QNN SDK           v2.22.6
结果:          QNN_COMMON_ERROR_INCOMPATIBLE_BINARIES
```

### 应对

| 模型 | 当前路线 | 原因 |
|------|----------|------|
| YOLOv5s | SNPE → DLC → INT8 → CPU（已跑通） | 视觉模型走 SNPE，不受 QNN 版本影响 |
| InceptionV3 | TF → DLC → CPU（已跑通） | 同上 |
| DistilGPT-2 | QNN IR 已生成，暂停 | 仅保留为工具链验证样本 |
| TinyLlama-1.1B | 等 HTP 恢复后走 QNN 原生 | 最终产品模型 |

### 两条腿走路

```
腿 1（现在）: 视觉模型 SNPE CPU + 规则引擎实时层 → 可 demo 基础避障
腿 2（等 HTP）: LLM QNN HTP + 结构化小脑 → 完整双层决策系统
```

这保证了 HTP 阻塞不会卡死整个项目。

## 五、VM 资源配置评估

### 当前配置

| 参数 | 当前值 | 评估 |
|------|--------|------|
| CPU | 4 核 (x86_64 软件模拟) | ⚠️ 无硬件加速，推理慢 10-50x |
| RAM | 8 GB | 🔴 LLM 部署关键瓶颈 |
| Disk | 40 GB (已用 18GB) | ⚠️ LLM 模型 + 校准数据需要更多 |

### 建议调整

| 参数 | 当前 | 建议 | 理由 |
|------|------|------|------|
| RAM | 8 GB | **12-14 GB** | 三模型驻留 + 系统开销。Mac 总 24GB，需留余量 |
| Disk | 40 GB | **64 GB** | 量化 LLM 2-5GB + 校准集 + 测试视频 |
| CPU | 4 核 | 保持或 6 核 | 多核有助并行推理 |

> ⚠️ 注意：VM 上所有推理都跑在 x86 CPU 模拟，真实性能必须上 QCS8550 真机才能评估。VM 仅验证管线逻辑正确性。

## 六、LLM 模型选型

### 候选小 LLM

| 模型 | 参数量 | FP16 大小 | INT4 大小 | 特点 | 推荐度 |
|------|--------|-----------|-----------|------|--------|
| **TinyLlama** | 1.1B | ~2.2 GB | ~0.6 GB | 最小可用，适合结构化小脑 | ⭐⭐⭐ |
| **Qwen2** | 1.5B | ~3 GB | ~0.8 GB | 中文好，指令跟随强 | ⭐⭐⭐ |
| Phi-2 | 2.7B | ~5.4 GB | ~1.4 GB | 推理能力强，但偏大 | ⭐⭐ |
| Gemma-2B | 2.6B | ~5.2 GB | ~1.3 GB | Google 出品 | ⭐⭐ |

### 推荐策略

1. **第一阶段（Phase A4）**：用 TinyLlama-1.1B 在 PC/CPU 上验证结构化决策逻辑
2. **第二阶段（Phase B3）**：HTP 恢复后优先把 TinyLlama 搬上板
3. **第三阶段（可选）**：如果中文场景需要，再试 Qwen2-1.5B

### DistilGPT-2 的角色

| 用途 | 说明 |
|------|------|
| QNN/ONNX/Transformer 工具链验证 | ✅ 已跑通，保留 |
| 最终产品模型 | ❌ 不推荐 — 偏通用文本生成，不擅长结构化决策 |

## 七、LLM 端侧部署现实约束

| 约束 | 说明 |
|------|------|
| 模型大小 | 7B 原始 14GB → INT4 约 3.5GB。手机端应选 1-3B 模型 |
| 推理后端 | QNN LPAI backend（支持 Transformer），需 QNN SDK ≥ 2.20 |
| 推理速度 | HTP 上 1B 模型 ~10-50ms/token，一次决策 50-200 tokens → 1-10s |
| 精度损失 | INT4 量化在 LLM 上损失比 INT8 视觉模型更大，需实测 |
| 当前限制 | VM 模拟不了 HTP/DSP，CPU LLM 推理极慢（可能 >500ms/token）|

## 八、关键风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 板端 HTP runtime 与 SDK 版本不匹配 | LLM 无法 HTP 加速 | ✅ **已通过双层架构解决**：实时层不依赖 LLM，Phase A 全部不依赖 HTP |
| VM 内存不足无法跑 LLM | Phase A4 阻塞 | 先扩 VM 到 12-14GB，或用 Mac 原生跑 LLM 验证 |
| VM 上 LLM 推理太慢 (>10s/次) | 无法真正 demo 实时性 | 明确文档记录"VM 仅验证逻辑，性能以真机为准" |
| 无真实硬件 | HTP/DSP 推理无法实测 | Phase A 全部在 CPU 完成，真机部分留待 Phase B |
| Mac 24GB 物理内存限制 | VM + Mac 同时跑吃紧 | VM 最多 14GB，Day 5 先用 8GB 测完再说 |
| 板厂联系不上 | 无法获取匹配 SDK/新版 BSP | Phase A 全面推进，不被单点阻塞 |
