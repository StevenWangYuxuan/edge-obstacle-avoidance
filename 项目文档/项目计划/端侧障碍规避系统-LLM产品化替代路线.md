# 端侧障碍规避系统 — LLM 产品化替代路线

> 日期：2026-07-03  
> 目标：在不放弃 QCS8550 + HTP 产品化方向的前提下，调整系统架构和 LLM 角色，提高项目落地成功率  
> 适用背景：当前板端 HTP runtime 与手头 SDK 版本不匹配；板厂暂时联系不上；但项目仍希望持续推进

---

## 一、为什么需要替代路线

原计划中的主链是：

```text
视频流 -> YOLOv5s -> InceptionV3 -> LLM -> 路径决策 -> 规避动作
```

这个方向在概念上成立，但从工程落地看，存在两个现实问题：

1. **LLM 直接位于实时决策闭环中，风险过高**
   - 端侧 LLM 推理时延抖动大
   - 输出自由度高，难以做稳定性和安全性验证
   - 即使 HTP 跑通，1B 级模型仍可能在 0.5~3 秒级，难以承担毫秒级避障控制

2. **当前 HTP 工具链阻塞了整条系统演进**
   - 板端 `/vendor` 中的 QNN HTP runtime 是 `v2.0.1.220706112757_38277`
   - 当前手头 SDK 是 `v2.22.6`
   - HTP 路径报 `QNN_COMMON_ERROR_INCOMPATIBLE_BINARIES`
   - 如果不调整系统设计，整个项目会被单点阻塞

因此，替代路线的核心思想是：

```text
不放弃 LLM
不放弃 HTP
但不让 LLM 成为第一阶段实时闭环的唯一决策器
```

---

## 二、推荐总方案：3 + 4 组合

这里的“3 + 4”指：

- **方案 3**：双层决策架构
- **方案 4**：把 LLM 缩成结构化的小脑，而不是通用聊天模型

这两者不是二选一，而是应该组合使用。

### 2.1 双层决策架构

新的系统主链建议改为：

```text
视频流
  -> YOLOv5s 障碍检测
  -> InceptionV3 障碍细分类
  -> 结构化场景描述
  -> 实时决策层
       -> 规则引擎 / 状态机 / 轻量策略模型
  -> 输出规避动作

同时：
结构化场景描述
  -> LLM 高层策略层
       -> 非实时策略建议 / 复杂场景解释 / 多步规划候选
  -> 提供给实时层作为约束或辅助
```

### 2.2 结构化小脑 LLM

LLM 不再承担“自由生成路线规划文本”，而是变成一个受约束的策略模型。

推荐输入：

```json
{
  "obstacles": [
    {"type": "cone", "x": 0.42, "y": 0.63, "w": 0.12, "h": 0.20, "distance_est": 2.3},
    {"type": "trash_bin", "x": 0.71, "y": 0.58, "w": 0.10, "h": 0.18, "distance_est": 1.4}
  ],
  "free_space": {
    "left": 0.68,
    "center": 0.12,
    "right": 0.55
  },
  "ego_state": {
    "speed_level": "slow",
    "heading": "forward"
  }
}
```

推荐输出：

```json
{
  "action": "BYPASS_LEFT",
  "confidence": 0.84,
  "reason": "center blocked, left corridor wider than right"
}
```

动作集合建议固定为：

```text
STOP
WAIT
SLOW_DOWN
KEEP_CENTER
TURN_LEFT
TURN_RIGHT
BYPASS_LEFT
BYPASS_RIGHT
```

这样做的好处：

- 输出空间可控
- 更容易量化
- 更容易做自动评测
- 更符合 HTP 上的小模型部署
- 系统更像产品，而不是聊天 demo

---

## 三、为什么这条路线更适合你的项目

### 3.1 符合“障碍规避”而不是“通用聊天”

你的项目目标是规避障碍，不是对话系统。

真正需要的能力是：

- 从视觉结果抽取结构化环境状态
- 在受限动作空间中做策略选择
- 在复杂情况时保留更高层次的 reasoning 能力

这更接近：

```text
结构化决策模型
+ 规则系统
+ 小型 LLM 辅助
```

而不是：

```text
通用生成式大模型直接控主链
```

### 3.2 更符合端侧实时性

根据现有测试和预估：

- YOLOv5 GPU 已接近 25 fps
- InceptionV3 GPU 已达 32 inf/s
- 真正慢的是 LLM

因此，第一阶段最合理的是：

```text
实时层由视觉 + 规则/轻量策略承担
LLM 只在必要时介入
```

### 3.3 更容易逐步接入 HTP

这条路线允许你分阶段推进：

1. 先把视觉主链稳定下来
2. 再把小模型 LLM 接成结构化决策器
3. 最后把 LLM 的 QNN HTP 路线补齐

这比“一上来就要求大模型直接跑进主闭环并完成所有规划”更稳。

## 四、模型路线建议

### 4.1 不再以 DistilGPT-2 作为最终目标

DistilGPT-2 在当前项目中更适合充当：

- QNN / ONNX / Transformer 工具链验证样本
- 最小可运行研究对象

但不适合作为最终产品模型，原因：

- 偏通用文本生成，不擅长结构化决策
- 中文能力弱
- 工程上不够贴近障碍规避场景

### 4.2 最终模型建议

如果后续 HTP 路线打通，建议优先试：

1. **TinyLlama-1.1B**
   - 最小、最现实
   - 更适合先跑通 HTP
   - 适合作为结构化决策小脑

2. **Qwen2-1.5B**
   - 中文能力更好
   - 更适合做策略解释和交互
   - 代价是模型更大、部署更难

不建议第一阶段就上：

- Phi-2
- Gemma-2B
- 更大的通用模型

### 4.3 更值得考虑的“非通用 LLM”方向

如果允许弱化“必须是通用大语言模型”的表述，实际上更适合本项目的可能是：

- 小型 decoder-only LLM，做结构化动作选择
- 小型 encoder-decoder 或 Transformer policy model
- 甚至是轻量多层感知机 / 小型时序 Transformer

从产品效果看，这类模型可能比通用聊天 LLM 更合适。

## 五、系统改造建议

### 5.1 实时层

实时层负责毫秒级反应，输入来自视觉模块，输出为最终动作。

可选实现：

- 规则引擎
- 状态机
- 代价函数 + 候选路径打分
- 小型策略网络

职责：

- 紧急停车
- 低速绕行
- 简单转向
- 安全阈值控制

这层应满足：

```text
无 LLM 也能工作
```

### 5.2 LLM 高层层

LLM 层负责：

- 复杂障碍组合下的策略建议
- 歧义场景的高层判断
- 输出结构化动作先验
- 生成可解释文本供调试或日志

不建议让它直接控制：

- 刹车时机
- 毫秒级转向
- 连续速度控制

### 5.3 融合层

实时层和 LLM 层之间加入融合规则：

```text
如果实时层判定危险阈值超限：
  直接 STOP / SLOW_DOWN

如果实时层无硬冲突，且 LLM 给出高置信建议：
  采纳 LLM 建议

如果 LLM 缺失/超时：
  回退到规则动作
```

这会让系统天然具备降级能力。

## 六、在当前条件下如何推进

即使板厂暂时联系不上，仍然可以推进以下工作：

### 6.1 现在就能做的

1. 完成视频流到结构化场景描述
   - YOLO 框
   - 分类标签
   - 估计相对位置
   - 可通行区域粗描述

2. 定义 LLM 输入输出协议
   - JSON schema
   - 固定动作集合
   - 置信度字段

3. 先做实时层
   - 规则引擎原型
   - 简单状态机
   - 回退逻辑

4. 用 CPU/GPU 或 PC 上模型验证“结构化小脑”
   - 先不要求 HTP
   - 先验证决策逻辑

### 6.2 等 HTP 工具链恢复后再做的

1. TinyLlama / Qwen 小模型 QNN 原生转换
2. QNN HTP 推理验证
3. INT4 / INT8 量化
4. 真实板端延迟与能耗评估

## 八、最终建议

如果目标是：

```text
LLM 真正跑在 HTP 上，并服务障碍规避系统的产品化
```

那么最推荐的策略不是：

```text
继续把通用 LLM 硬塞进实时主闭环
```

而是：

```text
双层决策架构
+ 结构化小脑 LLM
+ QNN 原生 HTP 部署
```

也就是：

- **系统层面选方案 3**
- **模型层面选方案 4**
- **工具链层面长期坚持 QNN 原生，不再以 SNPE 为 LLM 主线**

这是目前最接近“能落地、能扩展、能解释、能产品化”的路线。
